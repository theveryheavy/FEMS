## Release process

Maintainers manage releases intentionally; changes to this file do not publish a release.

1. Review and update this changelog, grouping user-facing changes under **Added**, **Changed**, **Deprecated**, **Removed**, **Fixed**, or **Security**.
2. Choose a version using `MAJOR.MINOR.PATCH`: increment MAJOR for incompatible changes, MINOR for backward-compatible functionality, and PATCH for backward-compatible fixes.
3. For a stable release, create and review a `vMAJOR.MINOR.PATCH` tag, then publish a GitHub Release with concise notes covering features, improvements, fixes, and breaking changes. Link the corresponding changelog section.
4. For a prerelease, use a SemVer prerelease identifier such as `v1.0.0-rc.1` and mark the GitHub Release as a prerelease. Do not advertise it as stable.
5. Development builds may be distributed from explicitly identified commits or prerelease artifacts after build and distribution workflows exist. Clearly label them as development builds; do not create misleading stable version numbers.
6. Verify the release assets and notes before publishing. Do not publish or automate releases without maintainer review.

There is no release version, build pipeline, or automated publishing workflow configured yet.
